其他引用该共享解锁规则的 macro 技能自动受益，不复制详细规则到所有入口，不改与本问题无关的资料或脚本。原始日历报告的错误不作为今后采集基线。

## 设计

### 1. 明确范围，等待有效加载

开始时记录项目身份、目标窗口起止、显示时区，以及单次事件还是窗口汇总。只有真实事件字段已出现、加载占位消失后才采集；切换页、标签或筛选后检查状态已更新。登录墙、付费遮罩、示例行与空表不是有效数据。

页面组件的图表时区不能套给未标时区的 Upcoming 卡片；只有日期时保留日期精度，无法确认窗口边界的记录留作边界待核项，不因猜测时区而丢弃。

### 2. 目标窗口覆盖检查

逐站记录已查看的页码／分页位置、排序方向、展开／筛选状态和覆盖范围。检查可见下一页、上一页及相关展开项。默认起始页可能位于历史或未来列表中间，不能假定第一屏是完整列表。

若观察证实列表按事件时间单调排序，可以在目标窗口两侧均取得范围外边界、目标页相关分项已读完后停止，不必遍历全部历史。若无法证明排序、列表属于速率变化节点、记录时区未知、动态加载未完或页码重复／停止变化，则不能据此宣称窗口完整；可通过可见筛选／展开继续核查，无法有界完成时记录具体停止原因并标记覆盖部分。巨大列表、权限或付费限制不要求无限翻页，不调用隐藏接口或绕过限制。

覆盖检查与事件可比性分别判断：读完 6 页历史速率记录仅证明这 6 页已读，不证明目标窗口全部释放量已取得；两个网站均打开也不等于完成双源核验。

### 3. 分来源记录，按同一事件对齐

轻量记录字段（可用 Markdown 表格，无需新增序列化框架）：

`项目身份 | 来源与 URL | 读取时间 | 数据版本 | 原日期/时区/精度 | 目标窗口 | cliff/linear/速率变化/累计 | 接收方 | 数量与单位 | 比例原标签/分母/时点 | 组件位置/页码 | 覆盖状态与原因 | 计划/估算/实际记录证据`

以项目身份、事件或窗口、接收方、释放类型为匹配依据。相同代币与日期不足以合并。展开不全、接收方不全、时区不明、事件与月度／7 天 emission 不同，则保留各站原值并写不可直接比较。

禁止将周释放速率当成该节点一次释放数量；无明确起止及速率变化证据，不从历史周速率外推本次月度总量。窗口汇总只有在覆盖足够、记录互斥无重复、类型和时间语义一致时才计算，并列出纳入／排除接收方。cliff 记录的窗口小计应明确为小计，不能替代另一站不同分组的单次事件。

FAQ／Insight 仅作待核线索；与结构化卡片不同则记录组件差异并核对项目原文，不自动选择较新组件或将两者拼接。项目原文只有估计曲线不能裁定第三方分钟级时刻为官方确认。

### 4. 输出分维度状态，不把缺失升级成冲突

每条记录分别表达：
- **采集覆盖**：目标范围已检查／部分／未取得；必须有边界或终止证据，且说明事件表、图表或速率节点各自覆盖了什么。
- **可比性**：同事件可比／口径不可比／字段不足；只在同事件且可比的记录中认定数量、日期等跨源数据冲突。
- **来源字段一致性**：一致／字段冲突待核／未取得；同页卡片与 FAQ 的差异不自动等于跨站事件冲突。
- **证据层级**：官方计划已确认／第三方估算待验证／未能核实／实际执行记录。官方确认仅覆盖原文明示的字段；实际执行需要相应证据，不能由未来计划推断。

允许状态同时存在，不用一个总标签掩盖多种问题。报告可保持简洁，但摘要须保留影响结论的缺口。“采集未完成”要求补采或具体受限原因；“口径不可比”保留双方原值；真正无法解释的可比字段差异才写“解锁数据存在差异，待核实”。

### 5. 日历输出检查

在技能与命令的收尾检查中要求：两站目标窗口覆盖已经检查并记录边界／受限原因；分项不能冒充总量；同事件比较满足时间、类型及接收方匹配；分母定义及时点可核实；来源字段冲突及限制在摘要中可见。

不完整记录仍可作为明确标注的线索进入日历，不让单站失败阻塞其他可靠事件。分母不适合时不计算“占当前流通量”，不据此触发 >5% 的高影响筛选。可另用影响范围与潜在供应规模说明高关注，但不能伪装成通过该数值阈值验证。

## 验证与验收

1. **静态检查**：三个目标文件的引用可解析、frontmatter 合法、共享规则保持单一来源、`git diff --check` 通过；不安装新依赖。按可用的既有验证器检查技能入口，工具不适用时记录实际替代与范围。
2. **实际浏览器核查**：通过内置浏览器验证 SUI 跨页遗漏已能被发现，记录窗口、页码、两侧边界和原时区；验证 ENA 全部公开页可读但仍属于历史速率节点，不能生成 10/2 完整总量；记录 Tokenomist 动态加载、卡片与 FAQ 差异及官方资料的确认边界。页面变化或访问受限如实保留，不能照抄本方案数值作为新实测。
3. **独立行为验证**：实现后交另一 subagent 在只读材料／临时目录中使用更新规则处理覆盖充分、缺一页、历史周速率、FAQ 冲突、未知时区／重复分页等案例。给原始材料与任务，不提供预期答案；检查是否先补采、是否区分状态、是否避免无效汇总／占流通比例与虚假官方确认。失败则修改并复核受影响案例。不写只匹配说明文字的测试。
4. **固定版本审查**：方案通过内置浏览器 ChatGPT Pro PLAN LGTM 后才委派开发；实现、必要验证和 PR 完成后将最终 diff／文件内容与验证证据交同样的 Pro CODE REVIEW。记录基线、HEAD、逐文件指纹／完整内容与审查原文；发现问题则修复并重新审查至 CODE LGTM。方案 LGTM 不替代代码 LGTM。
5. **合并与清理**：用户已明确授权本次提交、推送、PR、审查及合并。合并前同步最新 main，内容或语义发生变化必须重验与重新审查；不把旧 HEAD 结论冒充新 HEAD 审查。检查 PR 必需检查及冲突，合并后确认相关提交进入远端 main，再清理仅属于本需求且完全合并的分支／worktree；不触碰其他工作。

## 审查边界

ChatGPT Pro 对内联提供的完整文本／diff 进行审查。审查包不包含秘密、账户信息或无关个人材料。不能要求审查者声称独立取得 GitHub 仓库或实际操作浏览器；其能核验的文本指纹、现场证据评估与独立执行事实须分别记录。若 Pro 会话不可访问或需要用户登录，则保留方案、停止依赖该审批的开发，明确具体阻塞，不以其他模型替代用户指定审查者。
